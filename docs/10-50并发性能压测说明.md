# 50 并发挂号 P95 性能压测说明

| 项目 | 内容 |
| --- | --- |
| 文档编号 | PERF-OUTP-001 |
| 版本 | V1.2 |
| 适用基线 | PRD V1.7、AC-26、NFR-01/02/03、BR-03 |
| 读者 | 课程演示人员、验收教师、开发与测试同学 |
| 状态 | 2026-11-06 按 AC-26 实际执行并回填 PASS；审计并发连接饥饿修复后复验 |

## 1. 目的与范围

本次只回答一个可复验问题：**在本机演示环境下，50 个独立患者同时向同一 50 容量号源提交挂号请求时，挂号接口的 P95 是否满足 NFR-01 的 3 秒上限，并且号源/号序/余量仍正确**。AC-26 是正确性 + 本机延迟证据，不是生产 SLA、不是容量规划报告、不是 10 万数据量压测。`收费关键响应 ≤ 3 秒` 的全链路压测与 NFR-03 的 10 万挂号单查询压测仍为已知边界。

## 2. 被测环境与不变量

| 项 | 口径 |
| --- | --- |
| 被测接口 | `POST /api/registrations`，经 Spring Boot 8080 直连，不经过浏览器/Vite/Nginx |
| 后端 | Spring Boot 3.2.5、Java 21、模块化单体、JWT、JPA、Spring Security |
| 数据库 | 本机 MySQL `127.0.0.1:3306/outpatient`，V1.7 Hikari `maximum-pool-size=20`、`connection-timeout=5000ms`；`REQUIRES_NEW` 审计在业务事务释放连接后由外层切面写入，不预留同请求第二连接 |
| 并发控制 | `ScheduleRepository.findWithLockById` 号源行锁 + 同事务 `RegistrationRepository.findByScheduleForUpdate` 号序读取 + `uk_reg_queue` + `uk_patient_active_schedule` |
| 压测发起方 | Node.js 原生 `fetch`，同机 `Promise` 屏障同时释放；登录与夹具创建不计入响应时间 |
| 排除项 | 浏览器渲染、SPA 路由、WebSocket 广播、外网 RTT、冷启动、收费/医保链路、10 万行数据集 |

测试前需已启动 8080 后端与 MySQL，JVM 已由正常服务预热；`check:perf` 不需要 5173/5174、CDP 或 FAIL 模式后端。报告必须写明运行时的 Node、MySQL 与并发轮次，避免把单次本机结果外推为跨机器性能结论。

## 3. 夹具与数据隔离

1. 默认执行 3 轮；每轮生成唯一前缀、未来日期与唯一时段，互不复用号源。
2. 每轮用管理员 `/api/admin/schedules` 创建 `totalQty=50, remainingQty=50, status=OPEN` 的临时号源；通过 `/api/admin/catalog` 取一名真实医生/科室，确保外键完整。
3. 每轮直接写入 50 个临时患者和 50 个 `PATIENT` 登录账号，口令哈希复制演示患者账号；账号用户名与病历号只用于本轮，不改动既有演示账号。
4. 每个账号先单独登录取得 JWT，再用屏障让 50 个挂号请求在同一轮事件循环发出。
5. 每轮结束在 `finally` 中删除本轮 `operation_log`、`refund_record`、`registration`、`schedule`、`sys_user`、`patient`，并复查零残留；脚本异常退出时可按 `sql/mysql/02_data.sql` 恢复演示基线。

## 4. 指标与判定

- 单请求耗时：从屏障释放到 HTTP 响应 JSON 解析完成的客户端墙钟毫秒数，包含本机 HTTP、Tomcat 排队、Hikari 排队、数据库行锁等待、事务提交与响应序列化。
- 分位数：升序后按 nearest-rank 计算 `p50/p90/p95/p99`，同时记录 `min/max/avg`；P95 阈值固定为 NFR-01 的 `3000ms`。
- 吞吐：每轮成功数除以该轮从屏障释放到全部响应完成的墙钟时间；该值只描述本机单场景，不作为生产容量承诺。
- 正确性：单轮成功恰好 50 次、全部 `code=0`、HTTP 统一响应体状态正常、无 5xx、号序 1~50 不重复、数据库 50 条 `REGISTERED`、`remainingQty=0`、临时夹具零残留。
- AC-26 `passed=true` 必须同时满足：3 轮单轮 P95 与 150 次请求汇总 P95 均 ≤ 3000ms，所有正确性断言通过，报告 `errors=[]`。

| 环境变量 | 默认值 | 说明 |
| --- | --- | --- |
| `API_BASE` | `http://127.0.0.1:8080` | 被测后端地址 |
| `MYSQL_BIN` | 本机 MySQL 9.7 `mysql.exe` | 夹具写入/清理客户端 |
| `UI_OUT_DIR` | `docs/images` | 报告输出目录 |
| `PERF_ROUNDS` | `3` | 采样轮次 |
| `PERF_CONCURRENCY` | `50` | 每轮并发账号与号源容量 |
| `PERF_P95_BUDGET_MS` | `3000` | P95 上限，与 NFR-01 一致 |

## 5. 复验命令

在 `frontend/` 执行：

```bash
npm run check:perf
```

机器报告输出到 `docs/images/perf-50-concurrency-report.json`；报告含每轮 P95、汇总 P95、吞吐、号序/余量复核、数据库版本、Node 版本和清理结果。建议先执行 `npm run check:concurrency` 验证 20 抢 15 的业务拒绝，再执行本命令验证 50 并发的延迟与正确占用。

## 6. 结果回填

V1.5.4 的首次结果仅作为历史记录；V1.7 修复了 `afterCommit` 期间申请 `REQUIRES_NEW` 连接造成的并发连接等待：业务事务先完成并释放连接，外层 `AuditFlushAspect` 再独立落库，连接池设为 20、等待 5 秒。2026-11-06 按本轮代码重跑 `npm run check:perf`，机器报告 `docs/images/perf-50-concurrency-report.json` 为 `passed=true`；本机并发结论只以该报告为准，不外推为生产容量结论。

## 6.1 实测结果（2026-11-06）

| 指标 | 第 1 轮 | 第 2 轮 | 第 3 轮 | 汇总 |
| --- | ---: | ---: | ---: | ---: |
| 请求数 | 50 | 50 | 50 | 150 |
| 成功数 | 50 | 50 | 50 | 150 |
| 号序范围 | 1~50 | 1~50 | 1~50 | 每轮 1~50 无重复 |
| P95 | 705ms | 549ms | 525ms | 642ms |
| P99 | 732ms | 575ms | 547ms | 719ms |
| 最大耗时 | 732ms | 575ms | 547ms | 732ms |
| 墙钟时间 | 735ms | 578ms | 550ms | 1863ms |
| 本机吞吐 | 68.0 次/秒 | 86.5 次/秒 | 90.9 次/秒 | 80.5 次/秒 |

- 汇总平均 431.7ms、P50 420ms、P90 558ms；全部单轮与汇总 P95 均低于 NFR-01 的 3000ms 阈值。
- 每轮响应号序与数据库号序均为 1~50，50 条挂号单均为 `REGISTERED`，号源 `50/0/OPEN`；统一响应体 HTTP 状态 200，无 5xx。
- 3 轮临时患者、账号、号源、挂号与审计日志清理结果均为 PASS；演示库回归为 15 个账号、10 条排班、7 条挂号、0 条退费记录。
- 脚本首轮曾因 Windows `mysql.exe` 输出的 `\r` 残留于字段尾部、以及查询未限定临时患者而误判既有演示挂号状态；修复为按 `\r?\n` 分行并按临时 `patient_id` 过滤后复跑 PASS。该问题属于验收夹具读取，不是业务代码回归。

## 7. 解释边界

- 本机 50 并发通过只说明课程演示环境满足当前 NFR-01 的挂号 P95 口径；上线前仍需在目标硬件、连接池、网络、数据量与监控下重新压测。
- 10 万挂号单查询、收费/医保接口、混合读写、长稳运行、异常注入、回滚率、CPU/内存曲线不在本轮范围。
- 真实用户签名试用记录、批次库存锁、幂等键、HMAC 盲索引、Flyway 与专用 MySQL 账号仍按 RTM 的缺口或生产化边界管理。
