结论：上一版报告中的 P0-2 从「静态代码路径推断」升级为「运行态确认」。根因与静态审查一致：`WebSocketAuthInterceptor.java:121-125` 对 PATIENT 仍允许完整主题，`QueueEventPublisher.java:27-31` 向完整主题发布未脱敏 `board`。只要攻击者持有当天同医生队列的有效患者 JWT，即可手工构造 STOMP SUBSCRIBE 绕开 `frontend/src/main.js:855-857` 的 masked 选择。

补充：`ws-runtime-audit.json` 中 `doctor_other_full_rejected` 的 `passed=false` 是探针断言设计问题——脚本把「已发送 SUBSCRIBE 帧」记为 `subscribeSent=true`，而预期值设成 `false`；实际服务端已返回 ERROR，拒绝是生效的。该脚本的机器 `passed` 不可作为安全验收结果，须在 V1.7 改成「发送后收到拒绝」判定。

### 3.3 WebSocket masked 广播一致性：P1 已确认

运行态显示 REST 患者看板通过 `QueueService.board(...).maskedFor(user.getRefId())` 保留本人身份；但 `QueueEventPublisher.publish(...)` 向 masked 主题统一发送 `maskedFor(null)`，广播 3 行中所有 `patientId/patientNo/patientName` 均为 `null`。这确认了上一版报告的 P1-1：患者首次 REST 加载能看到本人身份，收到实时广播后本人身份会消失，实时与轮询/REST 展示口径不一致。

### 3.4 审计链路：P1 已确认

运行态临时创建一条 `pt0001` 挂号单并检查 `operation_log`：

### 3.5 文档证据边界

`docs/11-业务连通性与真实功能审计.md:91` 写「WebSocket 验证了真实连接与脱敏主题」。本轮实测表明：UI 报告的「实时队列已连接」只能证明连接状态；`read-only-connectivity-audit.mjs` 没有 STOMP 订阅、主题授权或广播 payload 断言；本轮新增 WS 探针才第一次形成完整主题/脱敏主题/拒绝订阅/广播 payload 的运行态证据，且恰恰证明 P0 风险存在。V1.7 必须先改文字边界，不能继续把连接状态表述为安全验收。

## 5. 对 V1.7 版本更迭建议的调整

上一份建议稿提出 V1.7「基线收口与安全验收加固」。运行态结果不改变方向，但把优先级调整为：

1. **先修 P0 WebSocket 授权**：PATIENT 只允许 `/masked`；员工完整主题白名单为 ADMIN/NURSE/本人医生；服务端拒绝必须生成机器报告和广播 payload 证据。
2. **统一患者队列脱敏**：REST、STOMP masked 广播、断线轮询三条路径同一口径；明确本人身份是否可见。
3. **补齐审计与事务口径**：挂号成功审计、操作人透传、SYSTEM 身份、`REQUIRES_NEW` 说明、退费级联口径。
4. **处理动态 UI 遮罩 FAIL**：先在验收脚本中等待 `#boot-screen` 真正移除，必要时把前端移除改为 `loadWorkspace()` 完成后触发；重跑 `check:dynamic` 到 PASS。
5. **文档先行收口**：改 `docs/11` 的 WS 证据边界，修正 `docs/02`、`docs/07`、`docs/00`、`README.md`、`docs/05`、`docs/04`、`docs/01` 的旧口径；统一报告 baseline；删除或补齐 DM8 脚本引用。
6. **补全量授权矩阵与工程化回归**：`check:authz`、JUnit 边界测试、`check:ws`、断线轮询交互、参数错误 400 映射、CHANGELOG/CI/lint/OpenAPI 仍为 V1.7 或 V1.8 规划。
