#### P0-2 患者可静态订阅员工完整队列主题

证据：

- `src/main/java/com/hospital/outpatient/queue/WebSocketAuthInterceptor.java:104-110` 对 `/masked` 主题要求患者有同医生/日期有效挂号。
- 同文件 `:112-125` 对非 masked 主题先放行 ADMIN/NURSE 与本人医生，最后仍允许「有有效挂号的 PATIENT」订阅完整主题并返回。
- `src/main/java/com/hospital/outpatient/queue/QueueEventPublisher.java:27-31` 向员工完整主题发送未脱敏 `board`，向 masked 主题发送脱敏 `board`。
- `frontend/src/main.js:855-857` 前端患者角色选择的是 `/topic/queue/{doctorId}/{workDate}/masked`，但服务端并未拒绝手工构造的完整主题订阅。

影响：按静态代码路径判断，持有有效患者 JWT 的客户端可能绕过前端约定，订阅员工完整主题并读取其他候诊者姓名、患者号等字段。由于本轮服务未启动，未做运行时复现；该问题应列为高优先级隐私风险而非已验证漏洞。

建议：V1.7 明确角色白名单：PATIENT 只允许订阅 `/masked`，对任何非 masked 队列主题一律拒绝；ADMIN/NURSE/DOCTOR 按既有规则授权完整主题。增加负向 STOMP 订阅断言：患者订阅完整主题失败、订阅 masked 主题成功；广播内容不得含其他患者 `patientId/patientNo/patientName`。

#### P0-3 WebSocket 证据边界被过度表述

证据：

- `docs/11-业务连通性与真实功能审计.md:91` 写「WebSocket 验证了真实连接与脱敏主题」。
- `scripts/read-only-connectivity-audit.mjs` 扫描未发现 STOMP 订阅、主题授权、广播 payload 或脱敏内容断言；该脚本主要是 REST 连通性与归属边界。
- `docs/images/ui-acceptance-report.json` 与 `docs/images/ui-dynamic-acceptance-report.json` 记录「实时队列已连接」，但没有证明订阅了哪个主题、是否收到广播、是否拒绝越权订阅。
- `docs/07-前后端分离架构与部署说明.md:82` 写「STOMP 实时连接」通过浏览器验收，同样属于连接状态证明，不是主题授权证明。

影响：现有 UI PASS 只能证明前端连接状态文本，不能证明「脱敏主题」或「越权订阅被拒绝」；把连接证据写成安全证据，会在评审或答辩中被追问。

建议：把 `docs/11` 边界改为「WebSocket 连接状态有 UI 证据；主题订阅授权、广播内容与脱敏 payload 尚无独立脚本」。新增 `check:ws` 脚本后再回填 PASS，不得先改结论。

### P1：下一版应完成的功能一致性与安全加固

#### P1-1 masked 广播与 REST 看板脱敏口径不一致

证据：

- REST 患者看板在 `QueueService.java:125` 使用 `maskedFor(user.getRefId())`，会保留本人身份，其他候诊者置空。
- `QueueEventPublisher.java:29-31` 对所有 masked 订阅者统一 `maskedFor(null)`，因此连订阅者本人身份也会被清空。
- `QueueView.java:41-45` 的脱敏规则依赖传入 `patientId`。

影响：患者首次 REST 加载能看到本人身份，收到 WebSocket 广播后本人身份可能消失；实时与轮询降级也可能显示不同字段。属于一致性问题，不是越权泄露。

建议：二选一并写入 PRD/SD：一是改为按用户目的地或患者专属主题做订阅级脱敏，保留本人身份；二是明确 masked 主题一律不显示所有患者身份，前端本人身份只从 REST 获取。无论选哪种，REST、WS、15 秒轮询必须使用同一展示规则。

#### P1-2 审计操作人、挂号成功审计与事务语义需收口

证据：

- `docs/03-详细设计说明书-SD时序图与状态图.md:52` 的 SD-01 写挂号成功时「独立事务写操作日志」。
- `RegistrationService.java:62-105` 的 `book(...)` 全程没有 `auditService.write(...)`；`RegistrationController.java:39-44` 也只把 `AuthUser` 用于本人校验，没有传入服务层写审计。
- `BillService.java:119` 的 `BILL_PRICE`、`QueueService.java:61` 的 `QUEUE_REPORT`、`:106` 的 `QUEUE_ARRIVE`、`:154` 的 `QUEUE_MISS` 存在 `null` 操作人或条件性 `null`。
- `AuditService.java:19-31` 使用 `REQUIRES_NEW`，业务事务回滚时审计记录仍可能保留。

影响：操作日志不能完整回答「谁在何时挂号/报到/划价」；文档「事务后一致」容易被误解为业务与审计同事务原子一致。

建议：把 `AuthUser` 透传到需要审计的服务方法，补齐挂号成功动作；定时任务使用明确的系统身份或 `SYSTEM` 口径；文档中把 `REQUIRES_NEW` 解释为「避免业务回滚吞掉审计，但不保证业务与审计同事务原子一致」。新增只读审计完整性脚本，检查关键动作的操作人、目标 ID、时间、重复次数。

#### P1-3 整单退费后的业务状态级联口径未闭环

证据：

- `BillService.java:190-211` 的整单退费只把 `fee_bill.status` 改为 `REFUNDED` 并写 `refund_record`。
- `BillService.java:262-273` 的 `markSourcesPaid` 在收款时把处方/检查单改为 `PAID`，并把 `registration.feePaid` 置真；退费方法没有对应的来源状态回退或禁止后续发药规则。
- 现有 `registration-cancel-refund-report.json` 覆盖取消/退号与挂号费退费，不等同整单退费后的处方、检查、发药状态机验收。

影响：静态口径上，退费后处方可能仍显示 `PAID` 并具备发药前置条件；重新划价时也可能因没有 `PENDING_FEE` 项目而失败。需要业务确认，不宜直接判为数据错误。

建议：在 PRD/SD 中明确「退费是否级联撤销处方/检查单、是否允许重新划价、已发药处方是否禁止退费」；按确定的状态机补事务与验收脚本。若课程范围不实现级联，必须在边界中写明「整单退费只做账务记录，不撤销诊疗单据」，并让发药/划价前置校验与该口径一致。

#### P1-4 全量端点授权矩阵与最小可见范围仍缺证据

证据：

- `scripts/read-only-connectivity-audit.mjs` 覆盖典型越权，但不是 12 个 Controller、51 个方法级端点、6 个角色与对象 ID 的笛卡尔矩阵。
- `VisitService.workbench`、`RegistrationService.workbench`、`BillService.workbench` 等员工工作台对部分角色返回全院或全状态列表；是否已按岗位最小化，需要逐一评审。
- `StatsService` 的医生工作量已在 V1.6 收敛到本人，但其他只读清单尚无统一「角色—资源—归属」规格表。

影响：典型 `403` PASS 只能说明样本安全，不能排除未测端点或工作台列表的横向越权。

建议：V1.7 建立 `docs/12-全量授权矩阵.md` 与 `scripts/full-authorization-matrix.mjs`：逐端点记录允许角色、拒绝角色、对象归属规则、预期 `code=403` 或 `code=0`；对工作台列表增加「医生只看本人、患者只看本人、收费/药房按业务需要」的明确口径；脚本必须自动清理临时数据。

#### P1-5 开发配置与令牌传递方式需列为生产化前置项

证据：

- `src/main/resources/application.yml:6-7` 使用 `root` 空密码；`:36`、`:39` 为固定 JWT/AES 密钥；`:37` JWT 有效期 720 分钟。
- `frontend/src/main.js:337`、`:1540` 把会话写入 `localStorage`；退出仅移除本地 token，无 refresh/黑名单。
- `frontend/src/config.js:16-22` 把 JWT 拼入 `/ws?token=...`；`WebSocketConfig.java:53-55` 从查询参数取 token，`WebSocketAuthInterceptor.java:70-75` 也兼容 STOMP `token` native header 或握手 token。
- 前端自写 `MiniStompClient`，15 秒轮询降级见 `frontend/src/main.js:755-883`；断线交互实测尚未形成脚本。

影响：课程本机演示可接受，但固定密钥、长时 JWT、URL 查询串 token 与浏览器本地存储不适合生产；代理、浏览器历史和访问日志可能留下令牌。断线轮询只有代码和连接状态证据，没有浏览器交互脚本。

建议：V1.7 至少把密钥、数据库账号、JWT 时长改为环境变量并补部署说明；把 WS token 从 URL 查询串迁移到 STOMP CONNECT header，或改用短时一次性 WS ticket；补「断开 WS → 15 秒轮询 → 恢复 WS」的浏览器交互验收。HttpOnly Cookie、refresh token 与黑名单列入 V2.0，不在课程阶段承诺。

#### P1-6 工程化回归保障不足

证据：

- `pom.xml:78-82` 有 `spring-boot-starter-test`，但 `src/test` 中 0 个 Java 测试。
- `frontend/package.json:7-19` 只有 Vite 与 Node 验收脚本，无 lint/test。
- 无 CI 配置、无 CHANGELOG、无版本 tag、无 ArchUnit/lint、无 OpenAPI、无 Flyway/Liquibase。
- 项目当前不是 Git 仓库；机器报告 baseline 版本字段不统一。

影响：授权修正、状态机修正和文档同步缺少低成本回归网；下一次改图或改代码容易再次出现「文档写 30 张、实际 33 张」这类漂移。

建议：补 JUnit 边界测试：2:59/3:01 过号扫描、过号重排、精神类药品双人签字、库存不足回滚、医保失败重试、并发抢号、退费状态前置。前端增加轻量 lint；若纳入 Git，使用 V1.7 tag 与 CHANGELOG；图集变更后必须重跑 `check:mermaid`、`check:diagrams`。数据库迁移工具可列为 V1.8 或 V2.0，按实际是否需要多环境部署决定。
