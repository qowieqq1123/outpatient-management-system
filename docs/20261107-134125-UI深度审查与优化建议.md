## 2. 总体判断：这样画“能验收”，但还不适合直接作为生产门诊工作台

### 2.1 已经成立的部分

- 视觉方向统一：深青色主色、米白底、琥珀色强调和珊瑚色异常，六个角色没有出现风格割裂。
- 登录页层级清楚：品牌说明、业务链路、身份选择、账号密码和演示提示的顺序合理。
- 工作台结构稳定：顶部会话区、角色导航、页面标题、统计卡、业务面板的骨架一致，便于不同角色迁移使用。
- 业务状态大多已中文化，金额统一保留两位小数；医保失败有红色内联提示，未伪装成收费成功。
- 390px 六角色均无横向溢出，既有动态 UI 验收报告未发现 JS exception 或 error/warning 日志。
- 颜色基本承担了语义：青色表示可用/成功，琥珀色表示待处理，珊瑚色表示失败、退费或风险。

### 2.2 当前不能忽略的结论

视觉完成度不能抵消真实交互问题。当前最需要优先处理的是：

1. 顶部“退出”按钮视觉存在，但实际点击没有绑定事件，不能完成退出。
2. 患者排班表把排班状态错误映射成挂号状态，出现“已报到 + 开放 + 可预约 + 已过期”的冲突表达。
3. 移动端和中等宽度的关键操作被统计卡和长表格推到首屏以下，导航/锚点滚动还会被固定顶栏遮挡。

## 3. 问题清单

### UI-P0-01：退出按钮是“看起来可用”，但真实点击无效

严重度：P0（必须修）  
证据：`frontend/index.html:99` 的按钮只有 `id="logout-btn"`，而 `frontend/src/main.js:1450` 的全局点击代理只处理带 `[data-action]` 的元素；`frontend/src/main.js:1469` 虽然存在 `action === 'logout'` 分支，但按钮没有 `data-action="logout"`。本次运行中点击、强制点击、回车和坐标点击均未回到登录页，也未清除本地会话。

影响：

- 用户无法可靠退出当前账号；
- 与登录页“退出登录即清除”的承诺冲突；
- 共用电脑或门诊窗口切换账号时存在会话残留风险；
- 这是功能缺陷，不是单纯视觉问题。

建议：给按钮接入现有 `logout` 事件分支，或单独绑定监听器；补充真实浏览器断言：点击退出后登录页可见、应用页隐藏、`localStorage` 中的 JWT 会话键为空。

验收标准：六个角色均能从任意滚动位置点击退出，返回统一登录页；刷新页面不会自动恢复旧账号；不会产生二次请求或残留 WebSocket 订阅。

### UI-P1-02：患者排班状态语义混用，且“可预约号源”可能包含已过期排班

严重度：P1（业务展示必须修）  
证据：`frontend/src/main.js` 的患者排班渲染将 `item.status === 'OPEN'` 映射为 `statusBadge('registration', 'TRIAGED')`，因此 OPEN 排班会显示挂号状态“已报到”；同一行还显示“开放”和“可预约”。已过期行又可能保留“可预约”标签，按钮却显示“已过期”。顶部计数只按 `remainingQty > 0 && status === 'OPEN'` 统计，没有排除日期已过期的排班。

截图表现：`docs/images/workspace-patient-desktop.png` 中同一排班行可见“已报到 / 开放 / 可预约 / 已过期”这一组互相冲突的语义。

影响：患者无法快速判断“现在能不能挂号”，也可能把历史号源计入“可预约号源”统计；门诊业务中的状态误读比普通视觉瑕疵更严重。

建议：

- 排班表只使用排班状态映射：开放、已满、已过期、已停诊；不要复用挂号状态映射。
- 每行只保留一个派生可操作状态，不要同时显示“可预约”和“已过期”。
- “可预约号源”统计排除过期日期、停诊和余量为 0 的排班。
- 操作按钮统一使用“立即挂号 / 已挂满 / 已过期 / 已停诊”，并让状态、余量和按钮三者一致。

验收标准：任何一行只能出现一套互不冲突的排班语义；历史日期不会进入“可预约号源”计数；状态变化后按钮同步变化。

### UI-P1-03：导航锚点滚动会把面板标题顶到固定顶栏下面

严重度：P1（导航可用性）  
证据：`.topbar` 使用 `position: sticky; top: 0; z-index: 30`，移动端 `.side-nav` 也使用 sticky；导航点击通过 `scrollIntoView({ behavior: 'smooth', block: 'start' })` 定位，但样式中没有 `scroll-margin-top` 或全局 `scroll-padding-top`。

截图表现：`docs/images/admin-maintenance-forms-desktop.png` 顶部直接从表单字段开始，账号/角色维护面板标题已被固定顶栏遮住；移动端管理台截图也出现同类定位不完整现象。

建议：为所有导航目标增加与顶栏/移动导航高度匹配的滚动偏移；滚动结束后保持面板标题可见。管理员页面较长，建议在导航定位后保留 12～20px 的上下文空间。

验收标准：点击任意角色导航后，目标面板标题、说明和首个操作区同时可见；桌面、722px 中宽和 390px 移动端均成立。

### UI-P1-04：收费失败重试的主操作不够“就地可见”，提示会覆盖操作区

严重度：P1（收费场景）  
证据：`docs/images/dynamic-cashier-retry-after.png` 中医保失败内联提示正确显示“待重试”，但“重新结算”按钮位于较长账单内容下方；底部 toast 叠在支付输入/按钮区域上方，可能遮挡正在操作的收费员视线。

建议：

- 在收费单标题或金额汇总旁提供固定的“重新结算”主按钮；
- 将支付通道、实收金额和主操作组成一个 sticky 或始终可见的操作区；
- 失败提示保留在账单内，toast 只做短反馈，避免覆盖表单控件；
- “医保失败”和“自费收款”需要更明显的操作分支，降低误点风险。

验收标准：1440×1000 和 390×844 下，选中 RETRY 收费单后无需滚动到底即可看到失败原因和主要下一步；toast 不遮挡输入框和主按钮。

### UI-P1-05：移动端首屏优先级偏向统计卡，关键业务操作被推到折叠线以下

严重度：P1（移动操作效率）  
证据：390px 截图中六个角色首先连续显示四张统计卡；患者的排班/挂号、护士的看板、医生的叫号/接诊、收费员的收费操作和药房的处方处理均需要继续下滑。医生/护士桌面画面还存在大块“暂无叫号”空状态区域。

影响：移动端更像“指标查看页”，不够像门诊现场的“操作台”；在窗口或走动场景下，最常用动作需要多次滚动。

建议按角色调整移动端顺序：

- 患者：当前叫号/我的号序 → 筛选与排班 → 统计卡；
- 护士：当前叫号和候诊队列 → 报到操作 → 统计卡；
- 医生：叫下一号/当前患者 → 病历与处方 → 统计卡；
- 收费员：选就诊/收费单 → 应收与支付 → 统计卡；
- 药房：待审核/待第二签/待发药 → 处方卡 → 库存表；
- 管理员：待处理告警和维护入口 → 统计 → 长表格。

不要求删除统计卡，可以在移动端折叠低优先级卡片，或只保留一行横向摘要。

### UI-P2-06：390px 顶栏和横向导航可用，但显得拥挤且缺少“还有更多”的提示

严重度：P2（移动体验）  
证据：`docs/images/mobile-workspace-doctor.png`、`mobile-workspace-admin.png` 等截图中，“门诊导视工作台”在 390px 宽度换成两行，退出按钮也呈窄高块；导航使用横向滚动，底部可见滚动轨迹，但没有明确的继续滑动提示。

建议：

- 移动端品牌缩短为“门诊工作台”，完整名称放在登录页或页面标题；
- 退出按钮固定为不换行的图标+文字或更紧凑的单行按钮；
- 导航增加右侧渐变/“横向滑动”提示，或在角色菜单较多时改为折叠菜单；
- 隐藏原生滚动条但保留可访问的键盘/触摸滚动。

### UI-P2-07：管理员维护面板信息密度偏高，权限和长表格不利于快速管理

严重度：P2（管理效率）  
证据：`docs/images/admin-maintenance-forms-desktop.png` 和 `admin-maintenance-mobile.png` 中角色表、账号表、两个表单连续堆叠；权限清单使用截断文本，移动端表格需要横向理解列关系，且没有搜索、筛选或分页入口。

建议：

- 角色维护、账号维护、排班维护拆成可切换的三个子面板或折叠区；
- 账号和排班列表增加关键词/状态/日期筛选，数量较大时分页；
- 权限清单在表格中显示摘要，点击后用抽屉/弹窗查看完整权限；
- 编辑表单打开后保留明确的“正在编辑：账号/排班”上下文，并提供取消编辑而不必滚动寻找“清空编辑”。

### UI-P2-08：管理员截图证据存在采集时机问题，不能直接作为排班画面质量证明

严重度：P2（验收证据质量，不等同于产品空白）  
证据：`docs/images/admin-maintenance-schedules-desktop.png` 基本只有顶栏和背景；`admin-maintenance-forms-mobile.png` 也只露出局部表单。`scripts/admin-maintenance-check.mjs` 在 `scrollIntoView({ behavior: 'smooth' })` 后只等待 250ms 就截图，而全局 `html` 使用平滑滚动，截图很可能发生在滚动动画中途。

判断：管理员 DOM 验收报告显示两个锚点、三个表单、角色列表和排班列表都存在，运行时没有 JS exception；因此这两张空/半空截图更像采集时机问题，不足以证明产品运行时真的空白。

建议：验收截图时禁用平滑滚动，或等待 `scrollY` 连续两次稳定后再截图；重新生成管理员画面证据，确保面板标题、表单和列表完整可见。

### UI-P2-09：键盘与辅助访问还可继续补强

严重度：P2（无障碍/长期维护）  
已做得好的地方是登录身份选择使用 `radiogroup`/`aria-checked`，密码按钮有 `aria-label`，消息有 `aria-live`。仍建议补充：

- 所有导航按钮增加当前项的 `aria-current` 或等价状态；
- 身份卡片按 ARIA radio 规范支持方向键移动和 roving tabindex；
- 增加统一的 `:focus-visible` 高对比焦点样式；
- 对表格横向滚动、状态颜色、固定顶栏遮挡做键盘/屏幕阅读器验证；
- 对小号的英文技术标签和弱对比辅助文字提供更清楚的中文说明。

## 5. 推荐的 V1.8 UI 修复顺序

### 第一批：先修真实功能和业务误导

1. 修复退出按钮事件绑定并增加浏览器回归断言。
2. 重做患者排班状态映射和可预约计数，统一排班状态/按钮语义。
3. 为 sticky 顶栏下的锚点增加滚动偏移，验证桌面、722px、390px。
4. 将收费 RETRY 的主操作和失败原因固定在可见操作区，避免 toast 覆盖。

### 第二批：优化移动端现场操作

1. 角色工作台改为“当前业务动作优先，统计卡次之”。
2. 压缩移动端品牌/退出区域，改善横向导航提示。
3. 对护士、医生、药房的空状态提供更短、更有行动指向的文案和按钮。

### 第三批：管理台和无障碍

1. 管理维护拆分为可切换子面板，增加筛选/分页和权限详情查看。
2. 补充 `focus-visible`、`aria-current`、身份卡片键盘操作。
3. 修正验收截图等待逻辑，重新生成完整管理员截图。

## 6. 本次审查的可接受边界

在修复 UI-P0-01、UI-P1-02、UI-P1-03、UI-P1-04 前，本项目可以作为课程演示、架构验收和内部原型展示；不建议宣称为可直接投入真实门诊窗口的生产 UI。

既有报告显示以下项目通过，但它们不能替代本次新增的退出按钮实测：

- `docs/images/ui-acceptance-report.json`：六角色桌面、390px 移动端结构、无横向溢出、无 JS exception；
- `docs/images/ui-dynamic-acceptance-report.json`：医保失败重试、六角色移动端、中文状态/金额和运行时日志；
- `docs/images/admin-maintenance-report.json`：管理员维护 DOM、接口闭环、运行时日志和夹具清理。

## 7. 最终结论

“这样画”作为 V1.7 的设计方向是可以的，品牌和工作台骨架已经形成；但下一版本必须从“画面完整”转向“操作优先、状态唯一、定位不遮挡、退出可用”。优先修复 P0/P1 后，再进行一轮真实点击回归和重新截图，才适合把 UI 作为稳定版本交付。
